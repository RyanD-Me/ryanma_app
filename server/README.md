# 二人麻雀 オンライン対戦サーバー

`index.html`(公開ページ)が接続する、WebSocket のオンライン対戦サーバーです。

- **対局はサーバーが進めます**(`gameSession.js`)。牌山を作り、両者から届いた操作(打牌・鳴き・和了・確認など)が
  その時点で合法かをエンジン(`mahjong-engine.js`)で確かめてから反映します。合法でない操作は受け付けません。
- 各プレイヤーには、その人が見てよい情報だけを送ります。**相手の手牌(局の途中)・牌山・まだめくっていない
  ドラ表示牌・嶺上牌・裏ドラ(公開前)は、中身の無い伏せ牌として送る**ため、ページ(HTML/JavaScript)を
  書き換えても見えません。点数などを画面の中で書き換えても、自分の画面の表示が変わるだけで対局には影響しません。
- 観戦者には両者の手牌を見せます(牌山は伏せます)。観戦者への対局データは **3分遅れ** で配ります
  (観戦を使った手牌の覗き見・通しの対策。一覧に出す局・点数も3分遅れ)。環境変数 `SPECTATOR_DELAY_MS`(ミリ秒)で
  変えられます(動作確認用。本番は設定しない=3分)。
- 牌山のシャッフル・ルームコード・起家や東家/南家の決定には暗号用の乱数を使います(配牌から牌山を逆算されたり、
  次に作られるルームコードを予測されたりしないように)。
- 観戦者には、対局者がまだ打っている局の局面は両者の手牌を伏せて配ります(局が3分より長いと、別の端末で自分の対局を
  観戦して相手の手牌を知れてしまうため)。
- プレイヤー名の見えない文字は取り除き、文字の向きを変える記号は名前の中だけに効くように閉じます。
- 同時接続数に上限があります(サーバー全体 1000・同じ接続元 20。環境変数 `MAX_CONNECTIONS` / `MAX_CONNECTIONS_PER_IP` で変更可)。
  超えた接続には「サーバーが混み合っているため接続できませんでした。」と返してすぐ切ります。
- 合法でない操作は拒否し、対局データ一式の送り直しは2秒に1回までにします(連打で通信量を増やされないように)。
- 相手が鳴けない捨て牌でも、1/7 の確率で 0.3〜1.8秒待ってから進めます(待ち時間で相手が鳴けるかどうかを悟られないように)。
- 持ち時間(打牌ごと+局ごと)はサーバーでも数えます。打牌ごと+残りの局ごと+通信の余裕2秒を過ぎても操作が届かなければ、
  サーバーが代わりに進めます(ツモ和了できればツモ、できなければツモ切り・見送り)。結果画面で確認が揃わない場合も自動で進めます。

## デプロイするファイル

`server/` の次のファイルを、そのままデプロイ先(Render に接続しているリポジトリ)に置いてください。

| ファイル | 内容 |
|---|---|
| `server.js` | 起動・接続の受け付け |
| `protocol.js` | メッセージの処理 |
| `roomRegistry.js` | ルーム・再接続・観戦・自動マッチング |
| `gameSession.js` | 対局の進行(合法手の検査・伏せ牌にした局面の配信) |
| `mahjong-engine.js` | 麻雀のエンジン(`npm run bundle` で `src/` から生成。手で編集しない) |
| `accounts.js` | アカウント機能(登録・ログイン・認証コード・名前変更・削除・メールアドレス変更・ゲスト番号) |
| `accountStore.js` | アカウントのデータの保存(Firestore) |
| `authMailer.js` | ログイン用のメール(Firebase の確認メール)の送信とリンクの確認 |
| `firebaseClient.js` | Firebase(Authentication・Firestore)の REST API を呼ぶ部品 |

`*.test.js` はテスト用なのでデプロイ不要です。依存パッケージは `ws` だけです。
ルール(`src/`)を変えたときは `npm run release`(または `npm run bundle`)で `mahjong-engine.js` を作り直し、
サーバーも再デプロイしてください(サーバーとページのエンジンが食い違わないように)。

## アカウント機能(Firebase)の設定

仕様は `docs/account-spec.md`。Render の環境変数に次を設定します。

| 環境変数 | 内容 |
|---|---|
| `FIREBASE_SERVICE_ACCOUNT` | **必須(秘密)**。Firebase のサービスアカウントの鍵(JSON ファイルの中身をそのまま)。リポジトリやチャットには貼らない |
| `FIREBASE_API_KEY` | 省略可(既定は本番のウェブ API キー。公開してよい値) |
| `FIREBASE_PROJECT_ID` | 省略可(既定 `ryanma-8be54`。鍵の `project_id` が優先) |
| `PUBLIC_URL` | 省略可。ログイン用メールのリンクの戻り先(既定 `https://ryand-me.github.io/ryanma_app/`) |

- `FIREBASE_SERVICE_ACCOUNT` が無いと、動作確認用にメモリ上で動きます(メールは送らず、リンクをログに出す。
  サーバーを止めるとデータは消える)。ローカルでの確認は `PORT=8090 PUBLIC_URL=file:///…/index.html node server/server.js`。
- `https://<サーバー>/health/firebase` で Firebase につながるかを確認できます(`{"mode":"firebase","ok":true}` なら正常)。
- Firebase 側の設定: Authentication のメール/パスワードを有効、承認済みドメインに `ryand-me.github.io`、
  テンプレート「メールアドレスの確認」の言語を日本語・「アクション URL」を公開ページ(`https://ryand-me.github.io/ryanma_app/`)に。

## 自動マッチングについて

- ロビーの「自動マッチング」を押すと、サーバーの待ち行列に入ります。同じサーバーで待っている人がいれば
  自動的にルームが作られて対局が始まります(どちらが起家の東家になるかはランダム)。
- 待っている間は「キャンセル」で待ち行列から抜けられます。待っている間に接続が切れた場合も自動的に抜けます。
- 組まれた後は通常のルームと同じ扱いです(再接続・退室なども同じ)。
- 待ち行列はサーバー1台につき1つで、同じサーバーに接続している人どうしが先着順に組まれます。

## 再接続について

- 通信が途切れても、座席は **5分間** 予約されたまま残ります。その間にクライアントが自動で再接続し、
  同じ座席に戻って対局を続けられます(切断中に相手が進めた分も、サーバーが保持している最新の
  対局データで追いつきます)。
- ページを閉じた・再読み込みした場合も、5分以内ならロビーの「対局に戻る」から復帰できます。
- 5分を過ぎても戻らなかった場合は、残っている側に通知してルームを終了します。
- どちらかが「退室」ボタンで退室した場合は、その場でルームを終了し、相手に「対戦相手が退室しました」と通知します。
  相手がその時に接続切れだった場合も、5分以内に再接続してくれば同じ通知を返します。
- 電波切れなどで切断の通知が届かない接続は、サーバー側は30秒ごとの ping/pong、クライアント側は
  25秒間の無通信で検出します。
- ルームの情報はサーバーのメモリ上にしかないため、**サーバー自体を再起動すると対局中のルームは失われます**
  (その場合は再接続できず、新しくルームを作り直す必要があります)。

## ローカルで動かす

```bash
cd 二人麻雀プロジェクトのルートディレクトリ
npm install        # package.json の依存(ws)をインストール
npm run server      # server/server.js を起動(既定ポート 8080)
```

起動すると `ws://localhost:8080` で待ち受けます。`frontend/index-ws.html` を開き、
ロビー画面の「サーバーURL」欄に `ws://localhost:8080` と入力してください
(同じパソコンの2つのタブ/ウィンドウで動作確認できます)。

ポートを変えたい場合は `PORT` 環境変数を指定します。

```bash
PORT=3000 npm run server
```

## インターネット上に公開する(相手と実際に対戦する場合)

2人が別々の場所から対戦するには、このサーバーをインターネットからアクセスできる場所に
デプロイする必要があります。Node.js が動く環境ならどこでも構いません。一例:

### Render / Railway / Fly.io などのPaaS

- リポジトリ(この `server/` を含むプロジェクト全体)をデプロイします。
- 起動コマンド: `node server/server.js`
- ビルドコマンド: `npm install`
- これらのサービスは環境変数 `PORT` を自動的に設定してくれることが多く、
  `server.js` はそれをそのまま使います。
- デプロイ後に発行されるURL(例: `two-player-mahjong.onrender.com`)の先頭を
  `wss://`(HTTPSでのデプロイなら必ず `wss://`。`ws://` ではブラウザ側が
  混在コンテンツとしてブロックすることがあります)に置き換えたものが接続先URLです。
  例: `wss://two-player-mahjong.onrender.com`

### 自分のVPSなど

```bash
npm install
PORT=8080 node server/server.js
# 常駐させるなら pm2 や systemd などをお好みで
```

リバースプロキシ(nginx等)でTLS終端して `wss://` として公開するのがおすすめです。

## 動作確認

ブラウザ以外からの簡単な生存確認:

```bash
curl http://localhost:8080/health
# => ok
```

動いている版(デプロイしたコミット)と起動時刻は `/version` で確認できます(自動デプロイで入れ替わったかの確認用):

```bash
curl https://ryanma.onrender.com/version
# => {"commit":"(Render が設定する RENDER_GIT_COMMIT)","protocol":2,"startedAt":"2026-09-26T..."}
```

### 自動デプロイされないとき

main を更新しても数分たって `/version` の commit が変わらない場合は、次を確認します。

1. Render の Events タブで、デプロイが始まって失敗していないか(失敗ならログに原因が出る)。
2. Settings → Build & Deploy: Repository が GitHub 連携で `RyanD-Me/ryanma`、Branch が `main`、Auto-Deploy が「On Commit」、
   Build Filters が空欄か。
3. 設定が正しいのに始まらない場合は、GitHub の更新が Render に届いていない。Repository の接続をつなぎ直す
   (2026-09-26 にこれで直した)。急ぐときは「Manual Deploy → Deploy latest commit」で手動デプロイする。

## 制約・注意点

- アカウントの認証はありません。ルームコードを知っている人なら誰でも参加できます
  (3人目は「満席です」エラー。総当たりでコードを試されることへの対策はありません)。
- サーバーはメモリ上にルーム情報を保持するだけで、永続化(再起動での復元)はしません。
- 1メッセージの大きさ(512KB)と、接続ごとの送信回数(10秒間に300回)に上限があります。超えると接続を切ります。
- create/join/rejoin/match には通信方式の版(`protocol: 2`)が必要です。付いていない古いページからは
  「アプリが古いため接続できません。ページを再読み込みしてください。」と返します。
- 観戦者は両者の手牌を見られますが、3分遅れなので、今まさに打っている局面を対局者に教えることはできません。
